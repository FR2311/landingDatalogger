SECCIÓN 2

Introducción

2.1 Propósito

El proyecto surge de una necesidad del INTI (Instituto Nacional de Tecnología Industrial): visualizar de manera sencilla y técnica las condiciones ambientales registradas durante las pruebas de laboratorio con robots.

El planteo inicial ubica un DataLogger dentro de la jaula del robot, en un punto específico, para medir temperatura, humedad y presión. Propone enviar los datos a un servidor del laboratorio mediante MQTT y una red que el texto denomina «mosquito». El servidor alojaría una web que leería archivos .xlsx y presentaría su contenido en un dashboard.

2.2 Alcance

El alcance se expresa mediante los siguientes requerimientos funcionales y no funcionales. Son objetivos definidos en el documento, no resultados de validación.

Requerimientos funcionales

Adquisición de datos
El sistema debe medir temperatura, humedad y presión en tiempo real a través de sensores.
Transmisión de datos
El sistema debe enviar los datos de forma inalámbrica utilizando el protocolo MQTT.
Almacenamiento local
El sistema debe guardar los datos en una tarjeta SD en formato .xls para análisis posterior.
Visualización de datos
El sistema debe mostrar los datos en una interfaz web en tiempo real con gráficas y valores numéricos.
Configuración del sistema
El sistema debe permitir configurar parámetros como frecuencia de muestreo, umbrales de alarmas y credenciales MQTT.
Alertas y notificaciones
El sistema debe generar alertas visuales en la interfaz web cuando los valores estén fuera de rango.
Exportación de datos
El sistema debe permitir descargar los datos almacenados en la tarjeta SD desde la interfaz web.
Autonomía del sistema
El sistema debe poder operar de forma autónoma alimentado por batería.

Requerimientos no funcionales

Confiabilidad
El sistema debe funcionar de manera continua y estable, sin pérdida de datos.
Rendimiento
El sistema debe transmitir y mostrar los datos en tiempo real con una latencia menor a 2 segundos.
Eficiencia energética
El sistema debe maximizar la duración de la batería optimizando el consumo de energía.
Seguridad
El sistema debe autenticar el acceso a la interfaz web mediante usuario y contraseña.
Integridad de datos
El sistema debe garantizar que los datos almacenados y transmitidos no se corrompan ni se pierdan.
Mantenibilidad
El sistema debe ser fácil de actualizar y mantener tanto en hardware como en software.
Usabilidad
La interfaz web debe ser intuitiva, clara y adaptable a diferentes dispositivos.
Resistencia ambiental
El hardware debe resistir condiciones de laboratorio, variaciones de temperatura y humedad.

2.6 Resumen ejecutivo

El objetivo es desarrollar un DataLogger autónomo, alimentado por batería, que se comunique con el servidor del laboratorio. En ese servidor se alojaría una página web para que los integrantes del laboratorio consulten el estado de las variables medidas.

SECCIÓN 3

Descripción general

3.1 Contexto del producto

En el laboratorio de robótica del INTI, el producto forma parte de un sistema mayor. El documento prevé entregar un DataLogger inicialmente y contempla que, con el tiempo, nuevos equipos puedan conectarse al mismo servidor del LABI para ser monitoreados de forma remota por su personal.

3.2 Funcionalidad del producto

La funcionalidad principal es permitir al equipo del LABI monitorear remotamente las mediciones ambientales obtenidas durante las pruebas y ensayos realizados con los robots y el material del laboratorio.

3.3 Características de los usuarios

3.4 Restricciones

3.4.1 Políticas reguladoras

El documento establece que la web del producto será software libre para el equipo del laboratorio.

PENDIENTELa redacción de este apartado quedó interrumpida en el original.

3.4.2 Limitaciones de hardware

El texto enumera como requisitos mínimos un DataLogger, una batería indicada como «1000 mA», un microprocesador, un circuito integrado que mida temperatura, humedad y presión, una red de comunicación con un servidor y una base de datos.

PENDIENTEFalta especificar la base de datos utilizada por Felipe. La unidad de capacidad de la batería también requiere revisión: el original indica 1000 mA.

3.4.3 Interfaces con otras aplicaciones

No se definieron interfaces con otras aplicaciones al redactar este apartado.

3.4.4 Función de control

Se prevé un único mecanismo de autenticación: acceso mediante usuario y contraseña proporcionados por el director del LABI.

3.4.5 Requisitos del lenguaje

La interfaz utiliza español y calendario gregoriano. El idioma no se modifica desde la configuración. El lenguaje técnico aparece en las unidades de las variables medidas y en los códigos RGB de los colores elegidos para las funciones de los gráficos del panel principal.

3.4.6 Protocolos señalados

Red
Se propone MQTT por su bajo consumo de recursos y volumen de datos; se contempla IP para identificar el servidor donde se aloja la web.
Web
El documento propone HTTPS para el cifrado e ICMP para mensajes de error de conexión entre el DataLogger y la web.

PENDIENTEConfirmar con Santiago Puleo y Felipe Risoli la viabilidad y la implementación de los protocolos propuestos. El original deja esta validación abierta.

4.5 Interfaces de comunicación

Comunicación entre sensores y datalogger
los sensores transmitirán las mediciones de temperatura, humedad y presión al datalogger mediante las interfaces de comunicación correspondientes.
Comunicación inalámbrica
el datalogger enviará los datos al servidor de manera inalámbrica, evitando la necesidad de una conexión física.
Protocolo MQTT
se utilizará MQTT como protocolo de mensajería para transmitir los datos desde el datalogger hacia el servidor. Este protocolo permite una comunicación eficiente y de bajo consumo.
Comunicación entre servidor e interfaz web
el servidor procesa los datos recibidos y los pondrá a disposición de la aplicación web para que puedan ser visualizados en el dashboard.
Comunicación con la tarjeta SD
el datalogger almacenará localmente las mediciones en una tarjeta SD en formato xls permitiendo conservar los datos incluso si se pierde temporalmente la conexión con el servidor.
